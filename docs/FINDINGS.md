# Findings

Where a finding contradicts the build spec, the finding wins.

## Part A — Static findings from the installed SDK (`@armoriq/sdk` 0.6.10)

Read from `node_modules/@armoriq/sdk/dist/*.d.ts` and `client.js` on 2026-10-10. Nothing here has
been run against the live service yet. Part B (spikes S0–S8) is still to do.

| #   | Spec says                                                           | Installed SDK does                                                                                                                                                                                                                                                                   | Consequence                                                                                                                                                                                          |
| --- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | U1: are `userId` / `agentId` required?                              | Optional. Constructor takes `Partial<SDKConfig> & { apiKey?, useProduction? }`. Missing IDs default to `'__sdk_multiuser__'`. Only `apiKey` is required, and it must start with `ak_live_`, `ak_test_` or `ak_claw_`, else `ConfigurationException` is thrown synchronously.         | Pass `apiKey` and `agentId`. Hashing happens server-side in `getIntentToken`. `planHash` is `token.planHash`; the Merkle root is `token.rawToken.merkle_root`.                                | `SignedPlan` is filled from the token, not from the capture.                                                                                                                                         |

| A15 | —                                                                   | Policy blocks and holds are only parsed by `invokeWithPolicy`. Plain `invoke` rethrows the raw HTTP error.                                                                                                                                                                           | The engine uses `invokeWithPolicy` for **every** call, including reads, so no policy response can be mistaken for a generic error.                                                                   |

### Design changes already made because of Part A

- Plan capture and signing use the real signatures in A2/A3.
- The verdict mapper handles `DelegationException` and `RevokedTokenError`, and `hold` events come
  from `onHold` (A5, A6, A14).
- Every call goes through `invokeWithPolicy` with `userEmail` set (A6, A15).

### Open risk to settle in S2

If a locally-raised `IntentMismatchException` leaves no trace in ArmorIQ (A8), the demo still has
real enforcement, but the required "dashboard screenshot of the BLOCK" has to come from a
proxy-side block instead. Candidates, in order of preference:

1. The `urgent-ceo` attack: `send_wire` blocked by `toolEnforcement`. For the call to reach the
   proxy the action has to pass the SDK's local plan check first, which means it only works if the
   proxy-side plan check or policy is what refuses it. S5 tests this.
2. Paying an unapproved vendor with `pay_vendor`, which is in the plan, so the call always reaches
   the proxy and is refused by recipient validation (S7).
3. `ArmorIQSession` in proxy mode, which reports enforcement decisions itself (A11).
